# YJ64 — Автономный инженерный цикл и план интеграции браузерных агентов

Статус: утверждённая архитектура; реализация выполняется по блокам
Репозиторий: concreteballs/YJ64-Engineering-Core
Ветка: main

Английский основной документ: [AUTONOMOUS_ENGINEERING_CYCLE_AND_MASTER_ROADMAP.md](AUTONOMOUS_ENGINEERING_CYCLE_AND_MASTER_ROADMAP.md).
Спецификация канала: [CHATGPT_CYCLE_BROWSER_AGENT_CHANNEL.md](CHATGPT_CYCLE_BROWSER_AGENT_CHANNEL.md).
Спецификация внешнего наблюдателя CI: [BROWSER_AGENT_FEEDBACK_BRIDGE_PLAN.md](BROWSER_AGENT_FEEDBACK_BRIDGE_PLAN.md).
Схема сообщений: [browser-agent-envelope.schema.json](../schemas/browser-agent-envelope.schema.json).

## 1. Что уже существует

В репозитории имеются:
- PostgreSQL-схема очереди задач и событий CI, атомарный захват задач с lease, ограниченные повторы и состояния blocked/completed;
- хранилище контрольных точек и механизмы восстановления неоднозначных запросов модели;
- заготовки ограничений провайдеров, бюджетирования, целостности частей больших входных данных;
- однократный WorkerRunner, обработчики CI-событий и отдельные рабочие процессы анализа логов/предложений исправлений;
- валидатор конверта браузерного агента и JSON Schema.

Это не означает, что автономный цикл уже работает целиком. Валидатор конверта не отправляет сообщения, WorkerRunner сам по себе не запускает фоновый цикл, а наличие миграций не доказывает успешную работу с реальной базой. По текущему журналу остаются непроверенными живое сохранение/получение задач, реальный вызов модели и сквозное продолжение выполнения.

## 2. Архитектура связи: два маршрута

### Маршрут A — обычный прямой обмен

1. ChatGPT создаёт отдельное неизменяемое сообщение-запрос.
2. Цикл проверяет область доступа, формат, срок действия и хэш; сохраняет запрос в постоянную очередь и возвращает подтверждение получения.
3. Цикл выполняет ограниченную задачу, сохраняет результат и ссылку на артефакт.
4. Прикладной Agent Communication Hub передаёт уведомление браузерному агенту.
5. Браузерный агент получает сохранённый ответ, а Hub доставляет его в общий чат, где его может прочитать ChatGPT.
6. Последующее сообщение создаётся как новый запрос с новым ID и ссылкой на родительский запрос.

### Маршрут B — сначала консилиум

1. Цикл определяет, что вопрос требует независимой оценки: высокая неопределённость, существенное расхождение моделей, междисциплинарные или критичные для безопасности последствия.
2. Цикл направляет в существующий консилиум конкретный вопрос, проверяемые утверждения и ссылки на доказательства.
3. Консилиум возвращает структурированный результат: вывод, основания, особые мнения/несогласие, открытые вопросы и ссылки на доказательства.
4. Цикл сохраняет и проверяет результат, затем формирует ответ.
5. Тот же Agent Communication Hub доставляет ответ через браузерного агента в общий чат.

Консилиум не запускается для обычных сообщений. Несогласие нельзя маскировать под единогласие. Браузерный агент не получает скрытые рейтинги моделей, тайные голоса и внутренние обсуждения консилиума.

## 3. Разделение ответственности

- **ChatGPT и пользовательский чат** — постановка задач, чтение ответов, согласование действий и уведомления. Чат не является хранилищем состояния цикла.
- **Автономный цикл YJ64** — очередь, выполнение задач, проверки, доказательства, решения о продолжении/остановке и запрос консилиума.
- **Agent Communication Hub** — прикладной транспорт между циклом, браузерными агентами и общим чатом. Он не должен быть встроен в GitHub worker.
- **Браузерный агент** — доставка ответа и разрешённое наблюдение за браузером. Он не заменяет цикл и консилиум.
- **Консилиум** — независимая оценка сложных случаев в рамках уже согласованной системы консенсуса.

## 4. Файловый канал GitHub и постоянное хранилище

Для начального файлового обмена использовать отдельный неизменяемый файл на каждое сообщение:

- `agent-bridge/requests/<message_id>.json` — запрос ChatGPT → цикл;
- `agent-bridge/receipts/<message_id>.json` — подтверждение или отказ;
- `agent-bridge/responses/<message_id>.json` — ответ цикла и ссылка на результат;
- `agent-bridge/agent-reports/<message_id>.json` — отчёт о доставке/наблюдении агента;
- `agent-bridge/council/<message_id>.json` — ссылки на запрос и результат консилиума.

Не использовать один изменяемый `inbox.json` или `outbox.json`: параллельные записи могут перезаписать друг друга. Каждое сообщение неизменно; переходы состояния записываются отдельными событиями с исходным ID.

GitHub-файлы — начальный интерфейс обмена и аудит. Авторитетное состояние планирования, блокировок, дедупликации, lease и больших артефактов должно находиться в уже существующих PostgreSQL queue/artifact store. Не создавать вторую очередь или дублирующую систему консенсуса. Секреты, токены, пароли и неограниченные персональные данные в репозиторий не записывать.

Каждый конверт должен содержать версию схемы, уникальный message_id, тип сообщения, idempotency_key, время создания/истечения, репозиторий/ветку, task_id, при необходимости run/attempt/commit, ограниченный payload и SHA-256. Повтор сообщения с тем же ID не должен повторять побочные действия. Просроченные, поддельные, повреждённые или выходящие за разрешённую область сообщения отклоняются.

## 5. Браузерные агенты и расширяемость

Hub должен иметь независимый от поставщика реестр адаптеров. Пользователь может добавлять, отключать, удалять и менять приоритет агентов без изменения кода инженерного цикла. Адаптер описывает платформу, возможности, способ авторизации, доступность, лимиты/стоимость, область данных и версию.

Начальные кандидаты:
1. **Perplexity Comet** — основной кроссплатформенный кандидат (Android/iOS/Windows/macOS); реальную связь с Hub необходимо проверить.
2. **Opera Neon с MCP Connector** — приоритетный кандидат для интеграции через MCP; требует разрешённого подключения и доступной браузерной сессии.
3. **Claude in Chrome** — дополнительный настольный вариант; расширение Chrome, не мобильный агент.
4. **Gemini in Chrome** — дополнительный вариант; автономные функции зависят от устройства, региона и подписки.
5. **Microsoft Edge Copilot** — дополнительный вариант с ограниченной доступностью.

Это кандидаты, а не уже подключённые интеграции. Нельзя считать обычную боковую панель полноценным браузерным агентом. Возможность навигации/действий включается только после проверки управления страницей, отчёта о результате, остановки задачи и надёжной передачи структурированного ответа в Hub. Агенты, умеющие только читать страницы, могут иметь ограниченную возможность read_page.

Если все агенты недоступны, ответ остаётся сохранённым со статусом ожидания доставки. Hub пробует следующий включённый пользователем адаптер в заданном приоритете. Для браузерных действий покупки, оплаты, отправки сообщений, изменения учётных записей, удаления и передачи личных данных требуется явное подтверждение человека. Содержимое страниц и ответы агентов считаются недоверенными данными; инструкции с веб-страниц не могут менять системные правила.

## 6. Очерёдность реализации — кратчайший безопасный путь к работающему циклу

Работать небольшими блоками. Не начинать следующие блоки, пока не пройдены критерии текущего.

### Блок 0 — проверить живую инфраструктуру (первый приоритет)
- Проверить актуальную версию Vercel receiver и текущую безопасную диагностику PostgreSQL; не полагаться на старые статусы и старые run ID.
- Устранить HTTP 503 по точному SQLSTATE и данным развёртывания.
- Добиться реального HTTP 202 и подтвердить соответствующие строки CI event/task в Supabase.
- Проверить на реальной базе enqueue, дедупликацию, claim/lease, восстановление после истечения lease и сохранение артефактов.
- Не запускать реальные вызовы модели, пока постоянное хранение не проверено.

### Блок 1 — один надёжный путь сообщений
- Повторно использовать существующие очередь, checkpoints и artifact store.
- Добавить сохранение request/receipt/response, parent/correlation ID, срок действия, хэш, дедупликацию и статус доставки.
- GitHub request-файл может быть входной точкой, но worker обязан переносить запрос в постоянную очередь.
- Сначала доказать тестовым стендом цепочку: запрос → постоянное подтверждение → сохранённый ответ. Не создавать вторую очередь.

### Блок 2 — один реальный вызов модели
- Подключить один провайдер, только если заданы секреты, проверенный профиль провайдера и глобальный/задачный бюджеты.
- Вызвать из планировщика уже существующие механизмы лимитов, резервирования, целостности payload и восстановления неоднозначного результата.
- Сохранять полный ответ как постоянный артефакт до завершения reservation и задачи.
- Пройти ограниченную задачу от claim до реального model request, сохранённого ответа и безопасного восстановления.

### Блок 3 — исполнитель задач и обратная связь CI
- Зарегистрировать узкий обработчик: читает план и журнал реализации, выбирает одну незаблокированную задачу и готовит небольшой разрешённый патч.
- Запускает проверки и связывает точный commit с конкретным GitHub Actions run.
- Получает проверенное событие завершения CI, классифицирует результат; исправления допускаются ограниченно и только при наличии новых данных.
- Не объявлять задачу завершённой по факту генерации кода или запуска CI.

### Блок 4 — автономное продолжение и независимость сессии
- Подключить сохранение checkpoint, контроль контекста, автоматическое создание новой model-сессии, восстановление после перезапуска worker и сверку неопределённых вызовов.
- Ввести лимиты задач, исправлений, времени, токенов и стоимости, подтверждения человека, pause/cancel и аварийную остановку.
- Проверить работу без телефона/открытого чата, восстановление после перезапуска и принудительную смену контекста без потери состояния.

### Блок 5 — браузерная доставка и консилиум
- Реализовать прикладной Agent Communication Hub и реестр адаптеров отдельно от GitHub worker.
- Подключить один проверенный адаптер и доказать доставку ответа цикла в общий чат.
- Добавить маршрут сложного запроса через существующий консилиум с сохранением особых мнений и доказательств.
- После этого подключать дополнительные браузеры, приоритеты и резервирование.

### Блок 6 — управление и полная приёмка
- Статус, уведомления, pause/resume/cancel, управление провайдерами.
- Сквозной тест: постоянный запрос → выполнение цикла → CI точного commit → сохранённый ответ → доставка браузерным агентом.
- Отдельный тест маршрута через консилиум, повторных/просроченных/поддельных сообщений, недоступности браузеров и аварийной остановки.

**Правило критического пути:** блоки 0–4 дают работающий автономный цикл, способный выполнять и проверять задачи. Блок 5 завершает требуемую интеграцию браузерных агентов, но интеграции конкретных браузеров не должны задерживать запуск первого рабочего цикла. Сначала блоки 0–2, затем исполнитель и CI.

## 7. Критерий готовности

Систему нельзя называть автономной, пока не доказано, что:
- задача сохраняется и выполняется после отключения телефона;
- worker восстанавливается после перезапуска и не дублирует побочные действия;
- реальный model request завершается сохранённым ответом;
- изменение проверяется CI именно для соответствующего commit;
- цикл продолжает работу или останавливается с ясной причиной;
- смена контекста модели не теряет состояние;
- браузерный агент доставляет ответ, а недоступность агента не теряет ответ;
- сложный случай проходит через консилиум и возвращается со всеми разногласиями и доказательствами;
- бюджеты, разрешения и аварийная остановка действительно работают.

До прохождения тестов система обозначается как частично реализованная, а не автономная.
