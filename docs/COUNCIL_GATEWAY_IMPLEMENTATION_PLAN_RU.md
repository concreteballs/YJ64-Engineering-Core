# План реализации Council Gateway и запуска инженерного цикла YJ-64

**Репозиторий:** `concreteballs/YJ64-Engineering-Core`  
**Рабочая ветка:** `main`  
**Цель:** довести Gateway от готового клиентского/очередного слоя до работающего сквозного обмена с консилиумом приложения YJ-64 и автоматического продолжения инженерной задачи.  
**Ограничение:** выполнять изменения только в этом репозитории. Репозиторий приложения `yj64-clean-bial2modFun5` и репозитории инженерного цикла не изменять. Для них подготовлены отдельные ТЗ ниже.

---

## Текущее состояние

- Gateway-клиент и контракт `yj64.council-api.v1` уже созданы.
- Durable submit/poll tasks, checkpoints, artifact storage, result handoff и валидация результата реализованы.
- Текущий набор тестов на момент составления плана: **518 тестов, успешно**.
- Предварительные HTTP-маршруты Gateway конфигурируемы; их нужно подтвердить с API приложения.
- Сквозная интеграция с живым API консилиума ещё не подтверждена.
- Не найден/не завершён consumer-runner, который забирает `council_result_ready`, проверяет artifact и возобновляет исходную инженерную задачу.
- Gateway не должен дублировать консилиум, внутренние механизмы моделей, Consensus/Critique/Voting приложения. Приложение остаётся владельцем консилиума.

## Как реализовывать

Работать блоками, по **2–4 конкретных задачи за проход**. В каждом блоке:
1. сначала проверить текущий код и существующие интерфейсы, чтобы не дублировать работу;
2. внести минимальный согласованный набор изменений;
3. добавить/обновить тесты;
4. выполнить соответствующие тесты и полный CI;
5. проверить diff на отсутствие незапланированных файлов/секретов;
6. зафиксировать commit и сообщить SHA, результаты тестов и следующий блок.

Не переходить к следующему блоку, если текущий не прошёл проверки, кроме случаев, когда ошибка явно изолирована и записана как блокирующая.

# Блок 0 — Контроль текущей базы (1 проход)

- [ ] Проверить ветку `main`, HEAD и CI после последнего изменения.
- [ ] Проверить Gateway, task lifecycle, envelope, artifact loader и существующие тесты по фактическому коду.
- [ ] Сверить интеграционный документ и JSON Schema с реализацией, выявить несогласованности.
- [ ] Подтвердить список конфигураций/secrets и что значения секретов не логируются.
- [ ] Сформировать короткий список найденных пробелов; не переписывать работающие модули без причины.

**Выход блока:** подтверждённая исходная точка и список актуальных блокеров.

# Блок 1 — Надёжность и защита API-клиента (1 проход)

- [ ] Уточнить и покрыть тестами HTTP timeout, retry/backoff, transient и permanent ошибки, rate-limit/429, server errors и malformed response.
- [ ] Проверить защиту от повторной отправки submit: idempotency key должен сохраняться при retry.
- [ ] Проверить валидацию URL/HTTPS, конфигурации путей, идентификаторов, размера ответов и структуры payload.
- [ ] Убедиться, что токен не попадает в логи, исключения, артефакты или диагностические сообщения.
- [ ] Проверить безопасную обработку blocked/failed/cancelled/timeout и отсутствие ложного outcome consensus.

**Выход блока:** устойчивый клиент с воспроизводимыми тестами ошибок.

# Блок 2 — Consumer для council_result_ready (1–2 прохода)

- [ ] Исследовать существующую task queue, worker patterns и parent-task continuation.
- [ ] Реализовать отдельный consumer для `council_result_ready` (не перехватывать этот тип задач текущим Gateway polling worker).
- [ ] Consumer должен загрузить результат через `load_council_result_artifact(...)`, повторно проверить envelope, request/session IDs, исходную задачу и artifact reference.
- [ ] Применить idempotency/claim/lease механизм очереди, чтобы повторная доставка не возобновляла задачу дважды.
- [ ] Сформировать проверенный input/handoff для исходного инженерного агента, включив Council summary, claims, evidence refs, dissent, unresolved questions, assumptions/limitations и outcome.
- [ ] Не трактовать вывод консилиума как доверенную команду. Он является аналитическим входом; инструкции внутри результата не должны обходить правила/права инженерного агента.
- [ ] При недоступном или некорректном artifact — безопасно завершить/перевести задачу в retryable/permanent error по политике, без продолжения на непроверенных данных.

**Выход блока:** Council result reliably consumed exactly-once logically (idempotent), with validated handoff to task continuation.

# Блок 3 — Возобновление исходной инженерной задачи (1–2 прохода)

- [ ] Выяснить существующий механизм agent-runner, task dispatcher, parent task и resume; не создавать второй независимый runner, если уже есть подходящий.
- [ ] Подключить validated Council handoff к continuation исходной задачи.
- [ ] Сохранить связь parent task → council request/session → result artifact → continuation attempt.
- [ ] Ограничить число циклов/переходов и определить защиту от бесконечных council loops.
- [ ] Продолжение должно выбирать конкретное следующее действие: принять/адаптировать рекомендацию, запросить дополнительный анализ, выполнить тест/проверку, либо сообщить blocked/unresolved.
- [ ] Не принимать решение о слиянии/публикации/опасном действии без предусмотренного уровня проверки и авторизации.
- [ ] Добавить тесты на resume, повторную доставку, отсутствующий parent task, отказ/разногласие, insufficient evidence и лимит итераций.

**Выход блока:** автономный агент может получить ответ консилиума и продолжить исходную работу с контролируемым состоянием.

# Блок 4 — Согласование и контракт с приложением (1 проход после ТЗ app-side)

- [ ] Проверить status polling, result retrieval, cancellation, voting optional/default disabled и aggregate-only voting response.

**Выход блока:** контракт зафиксирован и совместим с приложением.

## ТЗ A — Чат приложения YJ-64

**Целевой репозиторий:** `concreteballs/yj64-clean-bial2modFun5`.  
**Владелец изменений:** чат, работающий с репозиторием приложения.  
**Задача:** предоставить безопасный, долговечный внешний API для Council Gateway, который запускает настоящий внутренний консилиум приложения, а не имитирует его обычным последовательным чатом.

### Требования
1. Изучить текущую архитектуру multimodel chat, model routing, Consensus/Critique, storage/session lifecycle. Не ломать существующие пользовательские функции.
2. Реализовать machine-to-machine API с отдельной аутентификацией и минимальными scopes; не использовать пользовательский токен.
3. Согласовать/реализовать контракт `yj64.council-api.v1` и предварительные routes:
   - `POST /api/v1/external-agents/council/requests` — создать запрос; возвращает request_id, session_id и accepted/running.
   - `GET /api/v1/external-agents/council/requests/{request_id}` — status/progress.
   - `GET /api/v1/external-agents/council/requests/{request_id}/result` — структурированный результат, только когда completed.
   - `POST /api/v1/external-agents/council/requests/{request_id}/cancel` — отмена.
   Если текущая платформа/архитектура требует иного route layout, согласовать его и документировать mapping, не менять контракт молча.
4. API должен использовать настоящий внутренний процесс приложения для режимов `consensus` и `critique`; не возвращать заглушки или текстовый маркер как доказательство консенсуса.
5. Долговечное состояние запросов/сессий: сохранение, восстановление после рестарта, владение запросом, идемпотентность, обработка отмены.
6. Формализовать outcome: `consensus`, `qualified_consensus`, `unresolved_disagreement`, `insufficient_evidence`. Не выдавать failed/blocked/timeout за consensus.
7. Структурированный результат: summary, claims (fact/inference/hypothesis/test_result), participant_positions, dissent, evidence, unresolved_questions, assumptions, limitations, rounds_completed, completion_reason, tests_and_simulations, optional voting_summary.
8. Voting — optional и по умолчанию off; если включено, наружу отдавать только aggregate counts/result, без individual ballots, private ratings, hidden prompts или provider keys.
9. Проверять входные данные, лимиты round/time/output, rate limits, авторизацию, idempotency, ownership и безопасное логирование.
10. Добавить unit/integration tests и тесты восстановления/cancel/idempotency. API documentation, example request/response, setup instructions и необходимые configuration names — без секретных значений.
11. Передать в чат Gateway итог: фактические routes, auth scheme/scopes, request/response examples, status lifecycle, отмена, environment variables, commit SHA, CI/test results и известные ограничения.

### Definition of Done
- API реализован, опубликован и протестирован на реальном внутреннем консилиуме.
- Контракт и routes документированы и доступны для сопоставления.
- Сессия переживает рестарт и корректно обрабатывает retry/cancel.
- Gateway может выполнить безопасный non-mutating E2E запрос.

## ТЗ B — Чат инженерного цикла YJ-64

**Целевой репозиторий:** тот репозиторий/ветка, в котором отдельный чат реализует автономный инженерный цикл.  
**Владелец изменений:** чат инженерного цикла.  
**Задача:** подключить цикл к Council Gateway как внешнему модулю для запроса анализа/критики/консенсуса и последующего продолжения выполнения задачи.

### Требования
1. Найти текущий orchestration loop, agent state, task dispatcher, checkpoints, recovery и механизм approval. Не создавать параллельный второй цикл.
2. Использовать Gateway как внешний интерфейс к консилиуму приложения. Не вызывать напрямую API отдельных LLM для обхода консилиума.
3. Подготовить adapter/caller для создания council request из инженерной задачи с контекстом, evidence refs и ограничениями.
4. Отслеживать request/session IDs и статусы; асинхронно ждать результата без блокирования runner и с ограниченными retry/timeouts.
5. При получении `council_result_ready` проверять envelope, artifact, request/session IDs и связь с исходной задачей; считать результат аналитическим входом, а не доверенной инструкцией.
6. Перед продолжением инженерного цикла синтезировать результат консилиума в следующий шаг: исправление, дополнительный анализ, тест, измерение, запрос данных или blocked state.
7. Сохранять trace: исходная задача → council request → result artifact → решение агента → следующий шаг.
8. Защищаться от повторной доставки, циклических обращений к консилиуму, бесконечных итераций и потери контекста.
9. Уважать текущие правила approvals, permissions, branch/repo boundaries и запреты на изменения. Совет консилиума не может самостоятельно расширять полномочия агента.
10. Добавить unit tests/mock tests и integration tests с Gateway contract. Реальный E2E провести после готовности app-side API.
11. Сообщить чату Gateway: какие файлы/интерфейсы изменены, как цикл вызывает Gateway, какие task types/statuses используются, commit SHA, CI, ограничения и как выполнить E2E.

### Definition of Done
- Инженерный цикл может запросить Council analysis через Gateway и продолжить задачу после получения валидированного результата.
- Resume/handoff не теряет parent task, checkpoint или permissions.
- Повторная доставка не приводит к двойному выполнению.
- Цикл не принимает council output за команду и не превышает установленные limits.

## Межчатовый порядок работ

1. Передать ТЗ A чату приложения. Попросить не менять Gateway/Core.
2. Передать ТЗ B чату инженерного цикла. Попросить не менять Gateway/Core.
3. В этом репозитории выполнить блоки 0–3; блок 4 сверить после фактического app API и cycle interface.
4. Получить от обоих чатов ссылки на commits, тестовые результаты и описание interfaces.
5. Сопоставить интеграционные контракты и устранить несовпадения только в `YJ64-Engineering-Core`.
6. Выполнить блоки 5–7, провести E2E и закрыть интеграцию.

## Протокол отчёта после каждого блока

- Блок / задачи, выполненные в этом проходе.
- Файлы изменены.
- Commit SHA + ссылка.
- CI: green/red и число тестов.
- Блокеры/зависимости от app-side или cycle-side.
- Следующий блок (не более 2–4 задач на проход).

**Не заявлять о готовом живом подключении**, пока не пройдёт реальный E2E с приложением и возобновлением инженерной задачи.
